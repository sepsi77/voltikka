# Electricity futures services

Voltikka collects electricity futures end-of-day settlement prices from EEX so the site can build its own historical futures dataset.

Primary files:
- `EexFuturesService.php` — wraps the EEX public chart EOD endpoint and normalizes `settlPx`, `volume`, and `lotSize` series.
- `../../Console/Commands/FetchEexFutures.php` — Artisan command `futures:fetch-eex` for daily collection.
- `../../Console/Commands/BackfillEexFutures.php` — Artisan command `futures:backfill-eex` for fetching all history available from the public EEX API.
- `../../Console/Commands/FetchEexEuropeFutures.php` — `futures:fetch-eex-europe` for German power, TTF gas and EUA reference futures (market review only).
- `../../../config/eex_futures.php` — endpoint settings and the configured EEX instruments.
- `../../../database/migrations/2026_05_22_000001_create_electricity_futures_eod_prices_table.php` — storage table.

Important behavior:
- The fetch command collects discovery and maturity HTTP/connection failures that remain after the retry passes, missing or incomplete current-run prior-date FI proof for full runs, and checkpoint failures into one explicit Sentry Issue plus one safe aggregate Laravel log. Recovered failures do not alert. Normal empty out-of-range maturities never alert on their own. Per-maturity/discovery diagnostics are console-only and show exception classes, never raw HTTP text. Service methods keep throwing their original exceptions but do not log response bodies. Each command invocation owns a fresh reporter; repeated runs group by `eex_futures`. See `../../../AGENTS.md` for reporting rules.
- EEX requires the `Referer: https://www.eex.com/` header for browser-equivalent public chart requests.
- Public EEX API calls are throttled centrally in `EexFuturesService`: by default the first call runs immediately and later calls wait a random delay around 15 seconds (`request_delay_seconds` +/- `request_delay_jitter_seconds`). This intentionally makes backfills/daily fetches slow and polite.
- The scheduled production fetch runs at 04:00 Europe/Helsinki. An earlier 20:30 schedule ran successfully but FI settlement rows were still lagging, so fixed-term forecasts could keep using older futures; the overnight schedule gives EEX time to publish FI rows, but does not guarantee readiness by 07:30. Local bounded consumer ticks can wait until noon without rerunning the producer.
- The default full command writes a `running` same-date freshness marker with a UUID before date-range and instrument selection. Final writes compare that owner under the checkpoint row lock, so a late old command cannot replace newer run facts. Confirmed unexpected exceptions record failure for the owned date; this does not depend on the date when the exception occurs. It is ready only when it has no remaining fetch failures and this run extracted prior-date FI Base points for **all three tenors (month, quarter, year) on the run's latest prior FI trade date**. Metadata `current_run_latest_prior_fi_trade_dates_by_tenor` holds the latest date per tenor; `MorningJobFreshnessService::EEX_PROOF_TENORS` is the shared tenor list, and the morning gate rejects a ready row without a complete map (also pre-change rows). Reason: on 2026-10-07 the month discovery failed, so the run had only quarter/year rows; a quarter/year-only run must never be ready even without a counted failure. An old FI database row cannot prove current-run acquisition; the dependent gate queries the database separately for presence and age. Targeted and dry runs do not write this global fact.
- **In-run retry (2026-10-16).** A failure unit is one tenor discovery (the `price-ticker` probe for its representative market) or one market/maturity EOD request. After the main pass the command waits `retry_pause_seconds` (60) and retries only the failed units, through the same throttled service methods, for at most `retry_passes` (2) passes. A recovered discovery builds that tenor's requests for every market in the same pass. Failures are reported to the Issue only if they remain after the last pass; the checkpoint stores `failures` (remaining), `failures_before_retry` and `retry_passes`. More than `retry_max_failed_units` (25) failed units means an outage: no retry, because hundreds of throttled retries would add hours, and the existing failure outcome stays. The HTTP client's own 3-attempt retry is unchanged. Reason: 2026-10-07 (month discovery `ConnectionException`, plus one SE4 quarter request) and 2026-10-09 (one NO3 year request) each lost a whole morning of forecast and retail-premium output. A month-discovery recovery adds about 90 minutes (about 340 throttled calls), so the run still ends well before the 12:00 consumer deadline. No new schedule entry. Config keys are plain values, not environment variables. Tests: `FetchEexFuturesCommandTest` (they fake `Sleep`).
- A non-dry run that writes prior-date FI Base data bumps `ContractListCacheService`'s shared pricing-data version. List, company, ranking, contract-page, and prepared-page keys depend on this version, so forward Spot and reset estimates cannot retain the previous curve for up to 48 hours. Non-FI-only and dry runs do not invalidate contract pricing caches.
- Out-of-bounds maturity values return HTTP 200 with empty payloads (`price-ticker.data = []`, chart series empty), not a 404/error. The command probes `price-ticker` using one representative instrument per tenor and stops at the first empty maturity after valid maturities, so max delivery dates are discovered dynamically without repeating discovery for every market.
- The public EEX chart endpoint returns only about 45 days of history, so `futures:backfill-eex` means "fetch all publicly available history" rather than true deep history. The fetch command caps the requested start date to the configured `history_window_days` and defaults to re-fetching that full rolling window. Rows are upserted by instrument, maturity, and trade date, so reruns are safe.
- Default collection stores EEX Nordic System Price and Nordic zonal **Base Month, Quarter, and Year** futures for DK1, DK2, FI, NO1-NO5, and SE1-SE4.
- EEX maturity strings are `YYYYMM`: monthly maturities use the delivery month, quarterly maturities use the quarter start month (`01`, `04`, `07`, `10`), and yearly maturities use January (`YYYY01`).
- By default the command scans candidate maturities matching the EEX delivery dropdown shape: previous month + current/next months (`months_back`, `months_ahead` scan ceiling), next quarters (`quarters_ahead` scan ceiling), and next calendar years (`years_ahead` scan ceiling). The actual fetched set is the dynamically discovered contiguous valid range from the representative instrument, then the same maturity values are applied to all configured markets of that tenor. As of 2026-05 examples this means monthly `202604` through `202611`, quarters through `202801`, and yearly `202701` through `203201`.
- **Fixed 2026-11-01 (local): an unlisted maturity can return one all-null row.** The price-ticker sometimes answers `data: [[null, null, ...]]` instead of `data: []` (FNBM 202706 and 202812 on 2026-11-01). The old `maturityHasTickerData()` checked only `!empty($payload['data'])`, so discovery accepted every candidate up to the scan ceilings (25 months, 24 quarters, 12 years) and the 04:00 run made 793 EOD requests (02:01–05:34 UTC on 2026-11-01). For trade date 2026-10-30 only 268 area/maturity pairs had prices, so about 525 requests returned nothing; no wrong rows were written. A row now counts as listed only when it has at least one non-null value. Expected run: about 31 ticker + about 377 EOD calls, about 1 h 45 min. In October 2026 every zone's maturities were inside NP's range (NP lists 11 quarters and 10 years, zones 7 and 6), so the NP representative loses no listed zonal maturity. Test: `test_all_null_ticker_row_ends_discovery_like_an_empty_one`.
- **Continental reference futures (`futures:fetch-eex-europe`, 2026-11-01).** Phelix DE Base (`DEBM`/`DEBQ`/`DEBY`, area `DE`, POWER), TTF natural gas Physical month (`G3BM`, area `TTF`, commodity `NATGAS`) and EUA futures (`FEUA`, area `EU`, commodity `ENVIRONMENTALS`, product `EUA`, unit `TOCD` = t CO2) for the monthly market review (inventory G13–G15). Codes come from the public widget catalogue `POST https://api.eex-group.com/pub/customise-widget/filter-data-with-scope` and were checked with real EOD requests. The instruments are in `config/eex_futures.php` `europe_instruments`, never in `instruments`, so `futures:fetch-eex` and its checkpoint, FI proof and cache bump are unchanged. The command reuses `EexFuturesService` (same throttle) and the same table. Maturities are explicit (`maturity_rule` + `count`), not discovered: EUA lists only quarterly and December months, and discovery is unreliable (above). 21 requests, about 5 minutes. It never writes a checkpoint or bumps a cache, and it refuses an instrument whose area is in the Nordic list. Every pricing reader of `electricity_futures_eod_prices` (`MorningJobFreshnessService`, `VintageAwareReferencePriceService`, `FixedTermHedgeCostService`, `EexMarketReferenceCurveProvider`) filters `area = FI` (config `price_forecasting.fixed_term.area`) and `product = Base`, so these rows cannot enter Finnish pricing, forecasts or retail premiums. Keep that filter in any new reader. The catalogue also lists Finnish gas (`GFBM`, area `FIN`) and German THE gas; they are not collected.
- **Licence: EEX data must not be republished without permission.** The eex.com disclaimer (https://www.eex.com/en/disclaimer) says the site content may not be published or distributed without prior written approval of EEX AG, and commercial use needs express written approval. Public dissemination of EEX market data needs a Media Usage licence (https://www.eex.com/en/market-data/licensing-policies). Use these rows for internal analysis; a public review must not show EEX settlement values until the user gets EEX approval. This applies to the Nordic rows too.
- The current EEX product-code file does not expose Baltic power year future short codes for this endpoint. Do not invent Baltic instruments; add them to `config/eex_futures.php` only after verifying working `area` + `shortCode` combinations from EEX.

Useful commands:
```bash
php artisan futures:fetch-eex --area=FI --tenor=month --maturity=202606 --start-date=2026-05-04 --end-date=2026-05-08
php artisan futures:fetch-eex --area=FI --tenor=quarter --maturity=202607 --start-date=2026-05-04 --end-date=2026-05-08
php artisan futures:fetch-eex --area=FI --tenor=year --maturity=202701 --start-date=2026-05-04 --end-date=2026-05-08
php artisan futures:fetch-eex --dry-run --months-back=0 --months-ahead=1 --quarters-ahead=1 --years-ahead=1
php artisan futures:backfill-eex
php artisan futures:fetch-eex-europe                      # DE power, TTF gas, EUA; 45-day window
php artisan futures:fetch-eex-europe --short-code=G3BM --start-date=2026-10-01
```
