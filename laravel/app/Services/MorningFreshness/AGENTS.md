# Morning job freshness

This directory owns the small fail-closed freshness gate for scheduled retail-premium collection and fixed-term forecast generation.

## Primary files

- `MorningJobFreshnessService.php` records checkpoints, checks prerequisites, and writes one structured warning when a job is deferred.
- `MorningFreshnessResult.php` carries deterministic failure keys and messages.
- `MorningConsumerExecution.php` owns bounded consumer execution, durable exclusion and deadline reporting.
- `../../Models/DataFreshnessCheckpoint.php` defines checkpoint keys and statuses.
- `../../../database/migrations/2026_07_28_000001_create_data_freshness_checkpoints_table.php` defines durable storage.

## Rules

- A checkpoint is the latest fact for one key and effective date, not a run-history table. Contract-import version 1 also stores bounded pending completion proof in its JSON; `ContractImport/ContractImportCompletion` owns that local protocol.
- The effective date is the command `asOf` date in Europe/Helsinki.
- Both gated jobs require same-date ready `contract_import` and `eex_futures` checkpoints, current-run prior-date FI Base proof, and prior-date FI EEX Base database data within the configured age. The futures-adjusted forecast restores these EEX checks; retail-premium behavior is unchanged. Contract, unit-statistic, source-episode and publication recovery checks remain unchanged. A missing EEX requirement blocks publication-only recovery.
- Contract facts must contain `observed_source_observation_ids`, active contract IDs, and the exact statistics start and completion timestamps. Old snapshot-ID metadata and other missing or malformed facts fail closed.
- Versioned completion proof certifies the successful full completion at its write boundary; it does not freeze the market or cache generation for later readers. `ContractImportCompletion::readyCurrent()` belongs only at completion write/final-CAS guards, not in this service. New-manifest and legacy ready checkpoints use the same scoped rules below. EEX/cache invalidation and unrelated Spot, business-only or non-fixed publication must not add a global `contract_completion` failure. Relevant fixed-term publication after statistics remains the single recoverable `statistics_publication_order` failure when the other prerequisites pass. `pending_completion` never passes.
- When interpretation is enabled, retail-premium freshness checks every active checkpoint contract. Each must have exactly one observed episode in the checkpoint. That episode must equal the contract pointer, and its snapshot must equal the currently published interpretation snapshot. Observed pending contracts outside the active ID set do not block the current market.
- Fixed-term forecast interpretation checks start from the checkpoint active IDs, then use current contract facts and `ContractStatisticsSegmentClassifier` in the expected pricing basis. They require publication only for `Household`, `Both`, or null-target contracts classified as `fixed_term_6`, `fixed_term_12`, or `fixed_term_24`. Spot, Hybrid, OpenEnded, business-only, and other segment activity cannot make fixed-term statistics stale.
- Forecast checks additionally require at least one current-date fixed-term 6/12/24 `energy_price` statistic from `unitStatistics()` (`unit_statistics_v1`) for the PricingMode basis. Annual-method unit-shaped rows cannot satisfy this gate. The forecast builder handles each available duration independently, and gated zero output still fails.
- A required relevant fixed-term interpretation published after statistics started makes forecast statistics stale, including publication during the calculation.
- When this publication-order failure is the only forecast failure, the scheduled non-dry command recalculates the date's statistics from every current `active_contracts` ID with overwrite enabled. It then runs the complete gate again. No other failure and no dry run can start this recovery.
- The recovery captures a new Helsinki statistics-start time immediately before the direct `ContractPriceStatisticsService` call. The second check uses this override only for publication order; it still validates the stored checkpoint and every other fact. A relevant interpretation published after this new start keeps the gate closed.
- A successful recovery queues `WarmContractPriceStatisticsCache('weekly', 5000)` before forecast generation. An empty active-contract set fails instead of accepting an empty refresh.
- A ready EEX fact must contain the latest prior-date FI Base point extracted in that current run. The separate database query remains the data-presence and age check.
- Full upstream commands first overwrite the same-date checkpoint with a `running` start marker before acquisition. Contract runs install a UUID; later updates compare ownership, and required statistics hold the checkpoint row lock inside their existing transaction. A checkpoint-write failure stops the command. Scoped contract statistics never insert or replace global readiness. They lock an existing same-date row inside the statistics transaction; a missing row stays absent. EEX also installs a UUID and checks it under a checkpoint row lock at final writes. Confirmed unexpected producer exceptions mark owned checkpoints failed; an unavailable checkpoint store still produces a visible failure. See `../ContractImport/AGENTS.md`.
- Manual freshness remains opt-in with `--require-freshness`. Historical retail backfills bypass the freshness gate, but non-dry manual writers share consumer execution exclusion as described below.
- Keep failure messages concise and deterministic. Do not put exception messages, source payloads, credentials, or other secrets in checkpoint metadata or warning context.

## Bounded consumers (local implementation)

- The two existing commands accept `--scheduled`. It rejects every explicit date, selection, historical mode, overwrite and dry-run option, and enforces freshness itself. Default current-day scope only; no nested Artisan commands, dependency graph, new tables or producer retries.
- Independent five-minute background schedules run retail from 07:15 and forecast from 07:30 through 12:00 Helsinki. The time filter ends at 12:01 so process startup seconds cannot suppress the noon tick; the five-minute cron has no 12:01 execution. There is no overlap mutex: another tick must check the deadline even while an earlier writer runs. Noon admits no new execution. Work already executing may finish later that day; its late completion cannot erase the deadline alert. Write fences reject an old scheduled writer after Helsinki midnight. DST uses Helsinki calendar dates and local times.
- `morning_retail` and `morning_forecast` have distinct effective-date rows. Insert-or-ignore plus row-locked claims use the existing unique key/date constraint. All non-dry command modes, including partial/manual/historical selections, take their consumer's effective-date claim. Thus a manual run cannot bypass a same-date running or failed writer. A completed scheduled day is inert and also blocks later manual writes. Successful manual work can run again, but does not certify the scheduled default scope.
- Pure command-option validation and date/range resolution run once before any claim, recovery or output write. Invalid manual arguments return `INVALID` without a consumer checkpoint, so corrected calls remain possible. Historical retail defaults still use the minimum stored price date and yesterday. Manual model validation remains before the claim.
- Claims cover freshness preflight and execution. Not-ready scheduled dependencies return normal success and restore `waiting` without warning/error logs. Owner UUID, start/finish timestamps, safe reason and completion flag are durable. Exceptions and nonzero execution results are terminal `failed`; scheduled ticks return success after one safe failure log, so scheduler listeners do not repeat that alert. Failures before durable state can be saved return failure and log a safe class. Such storage outages cannot have durable deduplication.
- Running claims have **no expiry or takeover**. Interrupted work stays locked for inspection, including manual calls. Each output transaction locks and checks its owner. Forecast statistics recovery passes the same fence into the existing statistics transaction. No automatic overwrite, claim deletion or partial-output reconciliation is supplied. Inspect and separately approve any state/output repair before changing a claim.
- Completion requires nonzero built output and actual database output checks. Forecasts conservatively reject any pre-existing issue-date rows instead of certifying another model or a partial earlier write. Retail rows naturally span many days: current identity, financial/basis/method fields must match the built observation (four-decimal storage precision and JSON key-order tolerance), and the stored date extension must exist. A new published interpretation ID can keep the original immutable provenance only for the same observation key, source episode, snapshot and price signature; all other economic/source checks still apply. Existing metadata/date extension rules stay unchanged. An interrupted serial write cannot start a blind retry.
- The first noon-or-later tick reserves `deadline_alerted_at` under the row lock for each incomplete consumer, even if it is running or already failed. Later ticks cannot repeat it. Completion also checks a crossed deadline. Safe Laravel logs occur after the durable update, not inside the state transaction. This is one emission attempt, not a transactional log-delivery system: a process/storage/logging outage can prevent delivery. No outbox or new infrastructure is added.
- Exclusion is scoped to the command effective date. It does not freeze source data, coordinate unrelated statistics commands, or authorize cross-date historical repair. Existing producer/freshness rules remain authoritative. SQLite tests cover state ordering and output fences; they do not prove live MySQL blocking. Production depends on its existing unique constraint and InnoDB row locks.
- These changes are local only. No production operation or release is implied. See `../../../../tasks/bounded-morning-consumers/` for checks and limitations.
