# Official Spot price import

`SpotPriceImporter` is the single source of truth for persisting official ENTSO-E Spot prices used by `spot:fetch`, `spot:fetch-neighbours`, `spot:backfill` and `spot:repair-history`.

Important semantics:
- normalize API records and select electricity VAT from the record's Helsinki local time
- store 15-minute records in `spot_prices_quarter`; group their arithmetic hourly means by region and UTC hour in `spot_prices_hour`
- store direct hourly records in `spot_prices_hour`
- preserve existing records with `insertOrIgnore()` in chunks of 500; reruns do not revise prices
- complete hourly coverage for a half-open UTC range requires every exact expected hourly timestamp for the selected region; a partial set or off-hour rows cannot satisfy the check

ENTSO-E sends curve type A03 for FI and its neighbours: a point is omitted when the price does not change, and it is valid until the next point (the last point until the end of the time interval). `EntsoeService` expands A03 to every slot. Before 2026-11-01 it did not, so stored FI history has missing hours (46 in the local copy from 2025-09-30 to 2026-10-24) and hourly means calculated from 3 of 4 quarters (766 hours; October 2026 monthly mean 4.205 instead of 4.184 c/kWh VAT0). Insert-only reruns do not repair those stored values.

An older defect also exists: in 2022–2024 every second month (Feb, Apr, Jun, Aug, Oct, Dec) holds only its first day, so about 4,250 FI hours per year are missing (an earlier backfill of those months failed). Stored monthly means are therefore very wrong there (local copy: 2022-12 38.79 instead of 24.63 c/kWh VAT0; 2024-02 0.08 instead of 5.16).

`SpotPriceHistoryRepair` + `php artisan spot:repair-history --from=YYYY-MM --to=YYYY-MM [--region=FI] [--apply]` repair this. It is a dry run by default. It fetches one Helsinki month per ENTSO-E request, builds rows through `SpotPriceImporter::prepare()` (the same VAT and hourly-mean rules as `import()`), inserts missing quarter/hour rows, updates rows that differ by more than 0.0001 c/kWh (hours; `price_without_tax` is a MySQL single-precision FLOAT) or 0.00005 (quarters, DECIMAL(10,4)), and never deletes a row. After an FI apply it recalculates daily/monthly/yearly averages; the hourly `spot:fetch` would also do that, because `calculateAllAverages()` recalculates all of them. Past rolling 30/365-day rows are deliberately NOT recalculated: stored contract statistics used them as dated evidence, and `calculateAllAverages()` writes only today's rolling rows. Local dry run 2022-01..2026-10 (copy of 2026-10-28): 13,110 missing hours, 663 changed hours, 1,961 missing quarters; 46 of 58 monthly means move by at least 0.01 c/kWh. A production apply is a production data write: it needs explicit approval and a fresh dry run on production first. A01 series are parsed as before. When a zone publishes several sequences (DE-LU), only `classificationSequence` position 1 is kept: it is the coupled SDAC price (matched SMARD/Energy-Charts exactly on 2026-10-31).

Neighbour zones (`services.entsoe.bidding_zones`: SE1, SE3, EE, DE-LU) are stored in the same tables with their own `region` code by `spot:fetch-neighbours` (hourly at minute 25) and `spot:backfill --region=`. They get `vat_rate` 0, because Finnish VAT applies only to FI; their `price_with_tax` equals the VAT0 price. Every public reader filters `region = 'FI'` (checked 2026-11-01); keep that filter in any new reader. Neighbour runs never calculate averages or warm caches.

## Staged imports (`spot:fetch`, `spot:fetch-neighbours`)

Both commands use `App\Console\Concerns\StagedImport` (`../ImportPayload/AGENTS.md`, `tasks/staged-api-imports/`): the fetch step saves the raw A44 XML in a payload file under source `entsoe-day-ahead`, the store step parses that file with `EntsoeService::parseDayAheadPrices()` and inserts with `SpotPriceImporter::import()` in one transaction. `EntsoeService::fetchDayAheadResponse()` returns the raw response after the same timeouts and retry policy as `fetchDayAheadPrices()`, and throws `RequestException` for every answer outside 2xx (also a 3xx, which the HTTP client's `failed()` does not cover; review PR #31). The non-2xx check runs inside the retried operation (Laravel's `retry()` helper, 3 attempts, 1 s apart; CodeRabbit on PR #31), so a 3xx such as a 302 without `Location` (not followed) is retried like a 4xx/5xx or a connection failure; only the last failed attempt is thrown, so a staged fetch records it with `recordFailure()` as a failed unit with its status and body; `dayAheadRequest()` gives the base URL and query for a failure line. The query holds the `securityToken`: the payload writer removes it, and a test per command proves the key value appears nowhere in the decompressed file. Never log an ENTSO-E exception message.

- The window (Helsinki today through the day after tomorrow, half-open, UTC) is computed from the payload's `fetched_at` and recorded as header facts `period_start` and `period_end`.
- `spot:fetch`: one request, unit `{"region":"FI"}`. A failed request fails the fetch (`fetch_failed`, Issue stage `acquisition`) and leaves no payload. An empty or acknowledgement body is stored as 0 records with the warning Issue `empty_response` (exit 0). A store or after-commit failure keeps the Issue stage `save_or_post_import`; the Issue context gains `steps` and, for a `QueryException`, `store_error`. `calculateAllAverages()` runs inside the store transaction (S21: it writes `spot_price_averages`), so a failed average write also rolls back the run's price rows. The store parses first, then takes the cache lock `spot_store_v1:FI` (inner lock; the shared staged store lock `staged_import_store_v1:spot:fetch` is the outer one) (lease 3900 s, wait up to 60 s, the same lease reason as the forecast store lock in `../SpotForecasts/AGENTS.md`) and opens its own transaction inside it (`transactional: false`), so the commit precedes the release (review PR #31). Reason: a replay and a scheduled store running at the same time each computed averages from a snapshot without the other's rows. A lock wait that times out is the closed error `store_busy` (step `store`, exit 1, no write, payload kept, Issue stage `store_busy`). Tests: `FetchSpotStagedImportTest::test_a_store_that_cannot_get_the_store_lock_writes_nothing_and_is_busy`, `test_a_default_mode_store_waits_for_a_running_store_and_averages_over_its_rows` (two default-mode runs: the later one averages over the earlier one's committed rows) and `test_an_older_replay_waiting_for_a_newer_store_is_superseded` (an older replay that waited at the staged store lock while a newer default-mode store committed is refused `superseded`). `spot:backfill` and `spot:averages` do not take this lock. Only the nested `contracts:warm-price-statistics-cache` (a queue dispatch) runs after the commit. The averages are a recalculation over all stored FI hours, not a payload fact: their rolling 30/365-day rows take today's Helsinki date at store time, deliberately not a header fact, and a same-day replay writes the same rows. `SpotPriceAverageService` finds each average row by the calendar date of `period_start` (`whereDate`), because the `date` cast stores `Y-m-d H:i:s` and on SQLite a `Y-m-d` key missed the row, so a second run failed on the unique index (MySQL `DATE` columns were not affected). Acceptance tests on the real averages service: `tests/Feature/FetchSpotStagedImportTest.php`.
- `spot:fetch-neighbours`: one request per configured zone, unit `{"region":"SE1"}` etc. A failed zone (connection failure or any non-2xx answer after the retries) is a failed unit with its body; the other zones are still stored and the run exits 1 with `fetch_incomplete` (`complete:false`), as before. A store failure in one zone writes no row of any zone.
- Not date-bound (S9), but a `--from-payload` store of an older payload is refused (`payload_invalid`, `superseded`, no write) while a newer usable payload of the same command exists (shared rule, `../ImportPayload/AGENTS.md`; `spot:fetch` and `spot:fetch-neighbours` share the source directory but not the command, so they never supersede each other). Rows are insert-only, so a replay inserts nothing that an earlier store wrote. Replay is for the same Helsinki day only: the rolling averages of `spot:fetch` take the store's Helsinki date.
- `spot:backfill` and `spot:repair-history` still call `fetchDayAheadPrices()` and are not staged.

Commands keep responsibility for date ranges, ENTSO-E retries and errors, progress, delays, averages, output, and cache warming. Do not turn this service into a generic import framework or add a result DTO.

`EntsoeService` applies the `services.entsoe.connect_timeout` and `services.entsoe.timeout` limits before its retry policy. Their defaults are 5 and 30 seconds. The hourly `spot:fetch` schedule runs in Europe/Helsinki, uses one-server execution, and expires its overlap mutex after 60 minutes so an interrupted run cannot block imports for a full day.
