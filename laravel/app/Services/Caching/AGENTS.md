# AGENTS.md

Context for caching services under `laravel/app/Services/Caching`.

## `ContractPageCacheVersion`

Purpose:
- provides a cheap source-data fingerprint for high-traffic public contract listing and detail pages
- used by Livewire components that cache prepared view data until tomorrow, while still busting when contract/price source data changes

Important semantics:
- this is not full-response caching; components cache prepared view payloads to avoid expensive repeated contract list/detail assembly on canonical first-page loads
- `ContractListCacheService::getVersion()` is the primary pricing-data invalidation signal. A complete successful import activates it only after a verified staged replacement. A non-dry EEX fetch records durable replacement demand after writing prior-date FI Base data because futures change Spot and reset annual totals
- aggregate table counts/max dates are included to protect local/manual/test data changes and spot-average-dependent price calculations
- avoid expensive full-table JSON hashes here; this method runs to decide whether cached page payloads can be reused. `ContractPriceCacheEvidence` adds one bounded active-contract identity query (IDs, source/publication snapshot ownership and publication status), not full source or interpretation payloads
- calculated-cost payload v6 adds typed monthly included-energy package data
- payload v7 is the card/detail canonical-only current-value and real-term offer-copy boundary
- payload v8 is the company/SEO canonical offer-membership and JSON-LD boundary
- payload v9 adds exact typed canonical offer terms
- payload v10 adds real-term totals and offer savings for short BaseOnlyHybrid outcomes
- calculated-cost schema v11 invalidates old membership after `other` cadence recurring resets became listed estimates
- calculated-cost schema v14 adds the forward-Spot evidence payload and invalidates old rolling-Spot sort values
- `CalculatedCostPayloadSchema::VERSION` is the one calculated-cost shape version used by list, company, ranking, and prepared-page cache keys
- `ContractPageCacheVersion` keeps its own prepared-view wrapper version and also includes the shared `cs{version}` marker plus `PricingMode::cacheMarker()`
- Its Spot fingerprint includes all FI average period types, including corrected local rolling rows. Updated time, hour count, and overall/day/night price sums detect a same-date refresh even when row count and evidence dates stay unchanged.

## Shared annual price generations

- `ContractPriceCacheLifecycle` owns one atomic active descriptor: public integer version, private UUID generation, and creation time. The descriptor is always reread. When absent, bootstrap under the transition lock from the legacy contract version; legacy dated payloads are not imported as a verified generation. Cold test/local builds still work.
- `ContractListCacheService::refresh()` builds all eight presets privately and releases each hydrated set. Company/5,000 receives exactly the candidate/5,000 metric set, never the active accessor. Each write must succeed. Every required stored entry must match its expected serialized digest before activation. Active evidence must also remain unchanged during the build.
- Producer policy stage: interpretation/EEX/manual `bumpVersion()` now records a non-expiring demand revision under the short transition lock. It retains the exact active descriptor and all payloads; it does not retire the active generation. Each real invalidation increases the demand revision, but there is only one pending replacement demand. `requestRepair()` coalesces missing-payload demand without increasing an already pending revision. Its callers must not use `invalidate()` for HTTP misses. Old descriptors without `demand_revision` mean revision zero and need no rewrite. `demandRevision()` takes the maximum of the demand key and the active descriptor's satisfied revision. It reads `ACTIVE_KEY` directly, never through bootstrap while holding the transition lock. Losing only the demand key creates no new change, but the next invalidation/repair advances above the persisted satisfied floor. A candidate that captured a higher unmet demand still fails promotion if that demand key disappears during its build. Import completion's separate raw-demand proof stays strict.
- Activation, demand recording, bootstrap, cold payload writes, and bounded physical cleanup use the shared short transition lock; calculations and candidate payload writes do not hold it. Candidates capture demand revision. Promotion rejects changed demand or a changed active descriptor after required readback. The new active descriptor contains the satisfied `demand_revision` in the same pointer write, so a later demand cannot be lost through a separate demand-clear write. Company and list public versions advance only on promotion.
- All `refresh()` callers (scheduled/manual/import) use the same 1,800-second producer execution lease, with a ten-second acquisition wait. Promotion checks current lease ownership under the transition lock; an expired producer cannot publish or release a newer owner's lock. Lease loss is a non-retryable failure, retains demand, and requires durable candidate retirement. No expensive calculation holds the transition lock. Import candidate guards stay unchanged. Completion-write proof also requires that the captured cache demand revision is still current; this is not a permanent constraint on later morning consumers.
- Active list/company payloads use non-expiring writes. Generation keys retain schema and immutable pricing-mode markers but no calculation-day suffix. Rankings can expire, but rebuild from shared retained annual metrics, not current-date calculator calls. There is no midnight refresh schedule.
- Each generation tracks only its own written payload keys. Before switching the active pointer, the transition durably records the previous generation in `contract_price_cache_retired_v1` with a one-hour grace deadline. Failed candidates are registered on retirement. Manifests and retirement records do not expire: a cache TTL cannot physically reclaim abandoned MySQL rows. Payloads also remain until explicit cleanup, so in-flight readers retain them throughout grace. A late cold writer now rejects a changed active descriptor under the same lock before writing its manifest or payload; it cannot publish into an invalidated generation.
- `contracts:cleanup-price-cache` runs every five minutes with one-server and overlap protection. Each run examines at most 20 tracked generations and attempts at most 100 payload deletions. It rereads the active generation under the transition lock and never deletes it, even if an interrupted pointer write left it in the retirement index. It physically forgets exact tracked keys, records partial progress in the manifest, and removes the manifest/index entry only after successful deletion. Failures retain durable retry state and return a non-zero command exit for central scheduler reporting. Cleanup never scans the cache table, flushes a store, truncates a table, or deletes unrelated payloads or locks. Cleanup failures cannot undo activation. If cleanup-state persistence fails before activation, the pointer is not switched.
- Retained reads and current builds have separate guards. `guardBuildEvidence()` preserves the strict `ContractPriceCacheEvidence::isCurrent()` ownership/publication and exact source-identity checks. The producer fingerprint comparison is unchanged. **Never use `relational_pricing_published` as a canonical eligibility gate or fingerprint input.** Corrected deceptive canonical outcomes can remain listed while genuinely incomplete/conflicting outcomes stay excluded. Publication, pointer, and EEX changes alone no longer replace retained financial facts with exclusions. Retained reads use an ordered scalar active-ID/classification query, not immutable source JSON. Active retained rows keep their entire original price, phases, integrity, offers, `source_evidence`, and calculation timestamp. Inactive/removed IDs are excluded (removed in legacy mode); newly active missing IDs cannot calculate. Cached exclusions remain excluded until replacement.
- New list builds add optional `source_classification` transport metadata for contract type, pricing model, metering, audience, fixed term, company, and consumption bounds. The current-availability SQL query also selects only four JSON scalar leaves: recurring-schedule present/cadence and consumption-effect present/applies_to. SQLite integer and MySQL unquoted-string booleans normalize to effective `has_reset`, active `reset_cadence`, and `has_base_effect` (including the Hybrid fallback). A changed mechanism or scalar classification excludes that retained row until verified replacement. Period dates and prices alone do not exclude retained facts. No full pricing JSON, source donor, or futures preparation occurs here. Existing same-schema verified payloads without metadata keep availability-only compatibility; older nine-field metadata compares only its stored fields. Thus upgrade does not discard all retained prices, but older payloads cannot prove new mechanism compatibility until refreshed. No financial field, math, or calculated-cost schema changes.
- `CompanyListCacheService` wrapper schema is 3. Stored keys contain only generation/version, wrapper/calculated schema, mode, and consumption; publication identity is not part of the key. Each company row carries `_availability`, one 64-character SHA-256 string computed once per company build from the bounded scalar availability query, separate from source/publication evidence. The complete availability universe is never copied into company rows. Request memos include that identity. A missing wrapper or changed availability cheaply aggregates guarded shared metrics, with no annual calculator. Empty collections have no row marker, so each new request memo identity cheaply rebuilds an empty stored wrapper; reactivated cached contracts can then return without a stale empty company result. Both modes skip missing, excluded, or non-finite totals. Private candidate company builds still receive the exact candidate metric set, never the active lookup.
- For nonpreset custom consumption, company reads ignore any old persisted wrapper, require the exact shared custom metric set, and aggregate only in a request memo. Missing/expired custom metrics throw typed `ContractPriceCacheUnavailable`; no annual calculation, lifecycle write, or persistent company wrapper occurs. Availability and active-generation checks still reject aggregation races. Preset company wrappers retain their existing forever storage and behavior.
- This is not a database snapshot. Availability/classification checks stay current; strict interpretation identity checks apply to new builds, not retained prices. Retained phase prices, annual totals, and offer facts can remain from the previous calculation across source updates and midnight until verified replacement. This does not claim that the previous phase or offer is still current today. No canonical calculator semantics, publication, history, or statistics rules change.
- `ContractListCacheService::calculatedAt($consumption)` reads the stored payload's actual calculation timestamp; ranking wrapper v3 retains it in metadata. Ranking and prepared-page keys also include the private generation identity, so descriptor loss/bootstrap cannot collide with an older entry that has the same public integer version. Detail `heroVerdictNote()` uses the stored timestamp for `rankConsumption()` in Europe/Helsinki and omits the date when unavailable. It never labels retained rankings with the request date.
- `contracts:warm-cache --refresh` forces the staged replacement. Normal and `--pending` warmers check demand plus all eight preset/current schema/mode keys and company/5,000, then use the full staged replacement only if needed. Neither warms through public accessors. `--pending` is silent on success/no work; failure returns nonzero and retains demand. A per-instance minute schedule runs it in the background with 35-minute overlap protection and no `onOneServer`, because the file store is instance-local. Other schedules stay unchanged. Required import refresh failure remains `price_cache_refresh`; statistics timestamps and statistics-cache queue scheduling are unchanged.
- The shared read boundary now uses scoped `PublicPriceCalculationPolicy::allowsCalculation()`. Missing preset metrics on GET/HEAD or automatic HTTP initialization request idempotent lifecycle repair and throw `ContractPriceCacheUnavailable`. Only authorized explicit actions and CLI producers can build cold prices. Unsupported consumption misses return null without custom repair demand. Malformed payloads remain ordinary exceptions; they are not repaired or replaced with zero.
- `prepareComparisonForConsumption(int): ContractMetricSet` requires calculation permission even when a payload exists. It reuses a cached exact set or privately calculates the exact integer consumption using the strict current build guard, pre/post evidence/availability checks, two total conflict attempts, and manifest-owned lifecycle writes that reject promotion races. A subsequent GET can read that exact custom payload through `getCachedMetrics()`. Preset/support meanings stay unchanged. A replacement generation does not automatically copy custom profiles. The shared public `MAX_COMPARISON_CONSUMPTION = 150000` limits preparation to 1..150000 before cache bootstrap, pricing, or writes; callers must use the same limit and show validation feedback. No interpolation, rounding, or parallel handoff cache exists. Page/action wiring is a separate unit.
- Only newly written nonpreset custom handoff sets use a 30-minute TTL, with at most 64 live exact profiles per active generation. All eight presets and company payloads remain forever values. The existing generation manifest contains the exact owned key list and a bounded `custom_expirations` map; no new cache index or lease exists. Preparation checks capacity before expensive calculation and lifecycle writes recheck under the transition lock. Capacity throws typed `ContractPriceCacheUnavailable`, without evicting live profiles. Unknown custom GET remains null and never prepares. Request-only memos do not extend storage TTL. Generation promotion/conflict, demand floors, producer checks, and reader grace remain unchanged.
- Before a new custom calculation/write, expired manifest entries are physically forgotten, then removed from the manifest. A failed deletion or manifest write retains cleanup ownership and prevents admission; a later action can retry. A false forget can mean an already removed file/array entry: a one-second null marker on the exact owned expired key followed by checked deletion proves physical removal without restoring a price. Persistent failure leaves ownership intact. Expired-entry metadata does not accumulate over successful preparations. Retired cleanup ignores the expiry map and deletes the same owned key list. No preset, unrelated key, or active descriptor is deleted. This is action-driven expiry pruning, not a new scheduled active-generation sweep. Existing pre-change custom entries without expiry metadata are not retroactively migrated; a verified replacement generation drops them from active reads.

## Expired file payload disk reclamation

`cache:reclaim-expired-files` complements tracked generation cleanup. It uses only the configured default `FileStore`; other stores are a successful no-op. Default execution is a read-only full scan. `--apply` permits truncation, `--scheduled` selects the current epoch-minute first hash shard, and `--max-seconds=30` bounds scanning (manual catch-up can use up to 3600 seconds). The scheduler runs apply each minute on each instance, with a two-minute overlap mutex and no `onOneServer`, because file cache data is local.

The service streams only standard `aa/bb/<40-lowercase-hex>` entries whose hash matches both directories. The first shard cycles through all 256 values in 256 minutes; the second starting shard advances each cycle. Thus a large early directory cannot permanently block later leaf directories. A runtime limit returns nonzero and requires manual catch-up with a larger budget if a leaf cannot finish. No persistent cursor, full-store clear, cache get, deserialization, or directory deletion is used.

Only expired values with a valid ten-digit expiration and a bounded `a:` array or `O:` object type header qualify. Future/forever/zero expirations, malformed headers, other types (including serialized string lock owners), zero-byte markers, symlinks, hard links, and busy file locks stay unchanged. Header inspection does not validate the serialized body; arbitrary body corruption cannot be detected without reading it. No object is instantiated.

Apply opens an existing file with `r+b`, takes nonblocking `LOCK_EX`, checks regular-file pathname/device/inode identity and directory safety, then reads expiry/type under the lock. It truncates to zero instead of unlinking. This releases payload bytes while retaining the inode for Laravel `put`/`add` writers that already opened it and are waiting for the lock. Unlinking would lose those new per-key writes. Zero-byte markers and directories remain intentionally; normal FileStore access can later treat a marker as a miss. Counts report eligible logical bytes and actually truncated logical bytes, not filesystem allocated-block measurements. Errors and incomplete scans return nonzero with no paths, keys, payloads, or raw exceptions.

Focused test: `ExpiredFileCacheCleanupTest`.

## Bounded conflict recovery

Only `ContractPriceCacheConflict` is retryable: its named factories mean verified `evidence_changed` or `generation_changed`. Cold list reads have two total attempts. Each attempt rereads the active descriptor and evidence; no unpublished result or request memo crosses the retry. The outer prebuild evidence must still match before write, so a newly stable result cannot be guarded or memoized under an older identity. Company reads own the same two-attempt budget and disable nested list retries; they check their bounded availability identity before writing. No sleep, calculation lock, relational fallback, or fabricated zero is permitted. Verified retained prices are now permitted by the approved public read policy.

A staged refresh has two total full candidate attempts, not two per preset. It resets canonical Spot assumptions, episode anchors, Spot estimates, and the shared EEX provider memo before each candidate. Each attempt uses new contracts, a fresh descriptor/evidence fingerprint, and a new private UUID. A failed candidate must be durably retired with `required: true` before retry; retirement failure escapes as a storage error. Existing scheduled cleanup reclaims its tracked keys after grace. Active-pointer writes are never reversed. Independent interpretation/EEX demand changes are never cleared by an older candidate. Storage writes/readback use a separate non-retryable typed exception with closed diagnostic reasons. Unknown errors and invalid payloads also escape without retry.

`bootstrap/app.php` renders exhausted typed conflicts and expected `ContractPriceCacheUnavailable` as a plain Finnish HTTP 503, with `Retry-After: 30` and `Cache-Control: no-store, private`, and excludes only these two typed classes from automatic reporting. CLI callers still receive the typed exception. A proven complete full contract import can defer completion after exhaustion; other required failures still fail the checkpoint and emit one safe aggregate Issue. Unknown runtime exceptions retain normal reporting. Cost is bounded at two list/company attempts or two full eight-preset-plus-company candidates per call. This is not a source database snapshot.

`refresh()` accepts an optional import candidate guard. It checks the statistics-bound active/publication evidence and current run/claim ownership before the existing promotion boundary. A typed guard conflict uses the same two-total-candidate budget and durable retirement; it does not add retries per preset. No publisher mutex or source snapshot guarantee is added. Deferred imports re-run current-date statistics before a later refresh and bind completion-time proof to the resulting generation/fingerprint. That proof is checked at completion writes, not as a permanent cache-generation condition on morning readers. Later EEX/manual calls record retained-generation demand; fixed-term readers retain scoped publication-order recovery. See `../ContractImport/AGENTS.md` for the checkpoint row fence and bounded schedule.
