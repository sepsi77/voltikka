# Decisions

- Investigation was read-only. No production data, configuration, or deployment was changed.
- The correct current base energy price is 6.60 c/kWh. The latest upstream source snapshots contain three structured rows: Monthly 4.90 EUR/month, General 6.60 c/kWh, and General 0.00 c/kWh. Canonical interpretation identifies the zero General row as the consumption-effect placeholder.
- Root cause: both General source rows have the null UUID and the same type/fuse values. `CanonicalPriceComponentWriter` generates the same synthetic ID for both. Its `upsert()` processes 6.60 first and 0.00 second, so the zero row overwrites the real base energy price for that date. The older importer used `insertOrIgnore()`, which kept the first 6.60 row.
- The UI exposes the data defect inconsistently. Current pricing and timeline code prefer any positive row across all dates, so they fall back to the older 6.60 row. Price history uses raw rows and therefore charts the persisted zero. The current timeline date can also combine the older positive energy row with the newer monthly-fee date.
- Production evidence: General is 6.60 through 2026-07-22 and 0.00 on 2026-07-23 and 2026-07-24. Monthly remains 4.90. The first zero date is why the de-duplicated chart ends on 2026-07-23.
- This is broader than one contract. A read-only scan of 487 latest source snapshots found 29 duplicate synthetic-ID collision groups. Several Vaasan Sähkö Vaikuttaja variants persist zero; other suppliers can persist the last of two differing positive values.
- Recommended fix: make relational source-component normalization deterministic before writing. Collapse rows that map to the same generated ID before `upsert()`: prefer the first positive-price row and otherwise keep the first row. This restores the old importer's effective first-row behavior and matches the model's existing positive-price preference. Add a regression test for a 6.60 + 0.00 General pair and a test that reruns replace one date without allowing the later collision row to overwrite the selected value.
- Do not generate an ordinal ID and persist every duplicate yet. The relational calculator supports one component per type and does not have enough fields to assign multiple same-type source rows to semantic roles. Keeping all rows would move the ambiguity downstream.
- After deployment, repair the affected historical rows from immutable source snapshots. For Vaikuttaja, replace the false General 0.00 rows on 2026-07-23 and 2026-07-24 with 6.60. Then clear/bump the prepared contract-page cache. This is a production mutation and needs explicit confirmation.
- Keep the chart based on persisted selected prices after the ingestion and data repair. Do not add a broad UI rule that hides zero prices because zero is valid for some flat-fee/package contracts.
- Implemented the writer fix locally in `CanonicalPriceComponentWriter`: rows are keyed by the final `(id, price_date)` storage key before chunked upsert, a later positive row replaces a selected non-positive row, and later rows do not replace the first selected positive row.
- Added focused tests for a zero-first collision and for the production-order positive-then-zero collision during same-date replacement. The same-date test also verifies that a removed Monthly component is deleted.
- No repair command, deployment, cache invalidation, or production data update was run as part of local implementation.
